## 1. 충돌 해소 (A~D)

### A. 결제 모델: 단건 판매 → 횟수제 크레딧

**최종 결정**

Free / Basic / Pro 3단 횟수제 크레딧으로 전환한다.

| 등급 | 내용 | 가격 |
|---|---|---|
| Free | 계정당 1회 (가입 시 자동 지급) | 무료 |
| Basic | 분석 3회권 | 9,900원 |
| Pro | 분석 10회권 (9+1) | 24,900원 |
| 월간 구독 | Basic 자동 구독 시 매월 1회 무료 크레딧 | (후순위 스텝) |

- 리포트 열람 = 크레딧 1개 차감. **같은 리포트 재열람은 차감 없음** (열람 이력 기반).
- 진입 경로는 2가지 모두 크레딧 1회 차감으로 통일: ① 지도에서 핀 클릭 + 반경 선택 → 분석 ② 주소 직접 입력 → 분석 (기존 checkout 깔때기의 계승. 자기 매물 후보는 핀이 없을 수 있으므로 주소 입력 경로는 유지 필요).

**결정 근거 (왜 TOBE 안인가)**

1. 단건 9,900원은 "1회 사고 끝" 구조 — TOBE의 핵심인 **탐색형 사용(여러 후보지 비교)**과 맞지 않음. 입지 탐색 사용자는 핀 여러 개를 눌러보고 싶어하며, 횟수제가 이 행동을 수익화함.
2. Free 1회는 로그인 유도 미끼로 작동 — 로그인 게이트(C)와 맞물려 계정 확보 → 재구매 CRM 기반이 됨.
3. 회당 단가 하락(9,900 → 3,300원)은 AirROI 호출 비용 대비 검토 필요하나, `airroi_cache` 90일 캐시 + 반경 프리셋(D 참고)으로 캐시 히트율을 올려 방어 — 기존 비용캡(일일 호출 상한) 구조 그대로 유효.

**아키텍처 전환 설계 (Polar checkout·webhook·report_token → 횟수 차감형)**

- **크레딧 원장(ledger) 방식**: 잔액 컬럼 단일 저장이 아닌 `credit_transactions` 트랜잭션 테이블에 증감 이벤트를 쌓고, 잔액 = SUM(delta). 감사 추적·환불 처리·구독 지급이 전부 행 추가로 해결됨.
  - 주요 컬럼: `user_id`, `delta`(+3/+10/+1/-1), `reason`(signup_free / purchase_basic / purchase_pro / subscription_monthly / consume_report / refund), `ref_id`(Polar order id 또는 report id), `created_at`
- **Polar 상품 3개 생성**: Basic·Pro·(월간구독). `product_id ↔ 크레딧 수` 매핑은 환경변수 또는 매핑 테이블.
- **웹훅 개편**: `order.paid` 수신 → product_id 매핑 → `credit_transactions`에 지급 행 INSERT. **더 이상 웹훅이 report_token을 발급하지 않는다** (결제와 리포트 생성이 분리됨). 웹훅 중복 수신 방지용 `webhook_events` 테이블(event id UNIQUE) 신설 — 크레딧 이중 지급 방지 필수.
- **차감의 원자성**: "잔액 확인 → 차감 → 리포트 생성"을 Supabase RPC 단일 트랜잭션(`consume_credit_and_create_report`)으로 처리. 클라이언트 연타·동시 요청 시 이중 차감 방지.
- **report_token의 역할 전환**: "결제 증빙 겸 접근키" → "특정 분석 결과의 재열람 키". 리포트는 이제 로그인 계정에 귀속되며(user_id FK), 토큰은 열람 URL 식별자로만 유지.

**기존 자산 처리**

| 자산 | 처리 | 비고 |
|---|---|---|
| `/api/checkout` (주소→Polar 세션) | **변경** | 상품 선택(Basic/Pro) 기반 크레딧 구매 체크아웃으로 개편. 주소 입력은 결제와 분리되어 분석 시점으로 이동 |
| `/api/webhooks/polar` | **변경** | report_token 발급 로직 제거 → 크레딧 지급 로직으로 교체 |
| `report_purchases` 테이블 | **유지(역할 축소)** | Polar 결제 이력 + 기존 구매자 토큰 호환용으로 보존. 신규 리포트는 `analysis_reports`(신설)로 |
| `airroi_cache` (bedrooms/baths/guests 키 포함) | **유지** | Step E-1 캐시 키 확장이 그대로 신구조의 비용 방어선 |
| AirROI 일일 호출 상한·비용캡 | **유지** | 변경 없음 |
| Polar 단건 상품(현 ₩800 테스트) | **폐기** | 신상품 3개 생성 후 비활성화 |

### B. UX 플로우: 별도 페이지 → 동일 화면 인라인 리포트

**최종 결정**

`/explore` 단일 화면 내 인라인 패널(데스크톱: 사이드 패널 / 모바일: 풀스크린 바텀시트)로 리포트를 표시한다. 페이지 이동 없음.

- 흐름: 에어비앤비 핀 클릭 → 반경 선택(100m~2km) → 선택 반경 지도에 원형 오버레이 → [분석하기] → 크레딧 차감 → 같은 화면에서 리포트 패널 오픈.
- **기존 `/report/[token]` 자산은 "컴포넌트 추출 후 재활용 + 페이지 병행 유지"**:
  1. 리포트 섹션들(AirROI 통계, BedroomSelector, 건축물대장, 시뮬레이터, 면책문구)을 페이지에서 분리해 재사용 가능한 섹션 컴포넌트 묶음으로 추출.
  2. 인라인 패널과 `/report/[token]` 페이지가 **같은 컴포넌트를 공유** — 로직 이중화 없음.
  3. `/report/[token]` 페이지는 폐기하지 않고 유지: (a) 기존 구매자 토큰 URL 호환 (b) 재열람 시 직링크·공유 불가한 개인 열람용 (c) 인라인 패널 장애 시 폴백.

**결정 근거**

1. TOBE 명시: "사용자가 보고있던 화면에서 편하게 보고 닫을 수 있게" — 탐색(핀 비교) 흐름에서 페이지 이탈은 비교 행동을 끊음. 횟수제(A)의 "여러 번 분석" 수익 모델과 직결.
2. 기존 /report 페이지를 버리고 새로 만드는 것은 One-at-a-time 원칙 위반이자 검증된 자산 낭비 — 추출·재활용이 최소 변경 경로.
3. 병행 유지는 마이그레이션 리스크를 0에 가깝게 함 (기존 토큰 URL이 깨지지 않음).

**기존 자산 처리**

| 자산 | 처리 | 비고 |
|---|---|---|
| `/report/[token]/page.tsx` | **변경(추출) 후 유지** | 섹션 컴포넌트 추출, 페이지는 공유 컴포넌트의 얇은 래퍼로 |
| `BedroomSelector` + `/api/report/[token]/bedrooms-estimate` | **유지** | 인라인 패널에서 그대로 사용. API는 신규 리포트 식별자도 받도록 소폭 확장 |
| `ReportMap.tsx` | **변경** | 인라인 구조에선 /explore 지도 자체가 컨텍스트 — 패널 내 미니맵 필요성은 구현 시 판단(제거 가능성 높음) |
| `/checkout` 페이지 (`?dong=` 깔때기 포함) | **변경** | "주소 입력 → 결제" → "주소 입력 → 크레딧 차감 분석"으로 전환. 크레딧 없으면 요금제 안내로 연결 |
| 반경 값 | **변경** | 자유 슬라이더가 아닌 프리셋 스냅(100 / 250 / 500 / 1,000 / 2,000m) — `airroi_cache` 키가 radius_m을 포함하므로 프리셋이 캐시 히트율을 결정함. 자유값 허용 시 캐시가 사실상 무력화됨 |

### C. 로그인 게이트 위치

**최종 결정**

**무료 영역(동 단위 탐색 + 외도민 핀)은 비로그인 공개, 로그인 게이트는 "에어비앤비 핀 레이어부터"** 적용한다.

| 영역 | 로그인 | 크레딧 |
|---|---|---|
| 동 지도·경쟁밀도·외도민 핀 | 불필요 | 불필요 |
| 에어비앤비 핀 레이어 표시 | **필요** | 크레딧 지급/구매 이력 1회 이상 (Free 지급 포함 — 신규 가입 즉시 충족) |
| 리포트 분석 실행 | 필요 | 잔액 1개 이상, 실행 시 1개 차감 |

- 인증: Supabase Auth — **카카오 단독 (구글 보류)**.
- Free 1회 크레딧은 가입(첫 로그인) 시 자동 지급, `profiles.free_credit_granted` 플래그로 계정당 1회 보장. 소셜 로그인 필수 구조라 무한 어뷰징은 계정 생성 비용으로 1차 방어 (완전 방어는 범위 외).
- 핀 레이어 조건을 "결제 완료 후"(TOBE 원문)가 아닌 "크레딧 이력 보유"로 정의한 이유: 횟수제에선 잔액 0이 되는 순간이 반드시 오는데, 그때 핀이 사라지면 **다음 분석 대상을 고를 수 없어 재구매 동선이 끊김**. "이력 보유" 기준이면 Free 소진 후에도 핀은 보이되 분석만 잠김 → 재구매 유도 구조가 성립. TOBE의 의도(핀 = 유료 가치, 로그인 필수)는 그대로 충족됨.

**결정 근거**

1. TOBE 명시: "무료기능은 외도민 기준 업체만 확인가능", "유료기능 확인 : 회원 전용(카카오/구글)".
2. 무료 동 지도까지 로그인을 걸면 SEO·유입 미끼 기능(Phase 2-1의 존재 이유)이 죽음 — 미끼는 마찰 0이어야 함.
3. 에어비앤비 핀은 이 서비스의 차별 가치이므로 계정 확보 지점으로 최적 — "로그인만 하면 Free 1회로 핀+분석 체험"이 전환 깔때기.

**기존 자산 처리**

| 자산 | 처리 | 비고 |
|---|---|---|
| 로그인 없는 현행 구조 | **변경** | Supabase Auth 도입 (신규). 기존 `/explore` 무료 영역은 비로그인 유지라 기존 코드 영향 최소 |
| `report_token`만으로 접근하는 권한 모델 | **변경** | 신규 리포트는 로그인 세션 + user_id 소유 검증. 기존 토큰 리포트는 호환 유지 |
| Supabase RLS | **변경** | `credit_transactions`, `analysis_reports`, `profiles`에 user 단위 RLS 필수 (현재 service role 위주 구조에서 확장) |

### D. 데이터 소스 정합성: AirROI 좌표 핀 사용

**최종 결정**

"AirROI 좌표 `exact_location: false` → 맵 핀 부적합, 외도민만 핀 처리" 결정을 **폐기**한다. (§2에 CLAUDE.md 반영 문구)

- 유료 레이어: AirROI 좌표 기반 에어비앤비 매물 핀 (전제 2에 따라 사용 가능 확정).
- 무료 레이어: 외도민 핀 (기존 유지). 두 레이어는 색상 구분 + 체크박스 토글 (TOBE 명세).
- `exact_location: false`의 좌표 오차는 오히려 법적 안전장치로 재해석 (제미나이 법률 검토의 "반경 내 랜덤 노이즈 핀" 권고와 동일한 효과 — 건물 단위 특정 불가).
- **핀에서 파생되는 제약 2가지 (신규 확정)**:
  1. 핀 클릭 시 노출 정보는 익명 통계형만 — 숙소명·사진·개별 수익 절대 금지 (기존 변호사 상담 원칙 유지, 핀 위치만 예외).
  2. 핀 좌표는 오차가 있으므로 **건축물대장 조회의 입력으로 사용 금지** — 리포트 내 건축물대장 섹션은 사용자가 주소를 직접 입력(역지오코딩 추정 주소를 프리필하되 수정 가능)하는 방식 유지.

**결정 근거**

1. 전제 2로 좌표 사용 가능성이 별도 확인 완료됨 — 기존 폐기 결정의 근거(부정확 좌표 = 부적합)가 "부정확해도 핀 용도로는 충분 + 법적으로 오히려 안전"으로 뒤집힘.
2. TOBE 사용자 시나리오의 핵심 동선("에어비앤비 핀 클릭 → 반경 → 분석")이 이 데이터 없이는 성립 불가.
3. 외도민 단독 핀은 "인허가 기준"만 보여줌 — 사용자가 진짜 궁금한 "실제 영업 중인 경쟁 매물"과의 간극을 AirROI 핀이 메움 (CLAUDE.md [조사 필요] 항목에서 이미 인지된 니즈).

**기존 자산 처리**

| 자산 | 처리 | 비고 |
|---|---|---|
| 외도민 핀·경쟁밀도·폴리곤 (Phase 2-1 산출물) | **유지** | 무료 레이어로 그대로. 밀도 산정의 유일 소스도 외도민 유지 (핀 노출과 밀도 지표는 별개 결정) |
| "외도민이 경쟁밀도의 유일한 데이터 소스" 결정 | **유지** | 폐기 대상 아님 — 폐기되는 건 "핀 부적합" 판정뿐. 밀도 지표는 계속 외도민 |
| AirROI 통계 가공 노출 원칙 | **유지** | 핀 위치만 예외로 추가, 나머지 전부 유지 |
| `minbak_listings` | **유지** | 변경 없음 |
| (신규) `airbnb_pins` 테이블 | **신설** | 로드맵 §3 참고 |

## 3. 실행 로드맵 (Phase 2-2)

> 기존 로드맵의 "Phase 2-2 = iCal/스파이모드/과세판독"은 본 조정으로 **Phase 2-3 이후로 이월** (§4 참고). Phase 2-2는 TOBE 웹 구조 전환으로 재정의한다.
> 순서 원칙: 인증(2-2A)이 모든 것의 선행 조건 → 크레딧(2-2B) → 데이터(2-2C) → UX(2-2D) → 외피(2-2E) → 정리(2-2F). 각 스텝은 독립 배포 가능 단위.

### Step 2-2A — 인증 기반 (Supabase Auth: 카카오·구글)

- **(a) DB**: Supabase Auth 활성화(`auth.users` 기본 제공). 신규 `profiles` 테이블(user_id PK→auth.users FK, `free_credit_granted` boolean, created_at). RLS: 본인 행만 조회.
- **(b) API**: OAuth 콜백 라우트(`/auth/callback`), 세션 미들웨어(보호 대상: 핀 레이어 API·분석 API). 로그인/로그아웃 UI.
- **(c) 모델 태깅**: **설계 Opus 1회** (세션 전략 — @supabase/ssr 쿠키 기반 vs 기타, RLS 경계, 미들웨어 보호 범위) → **구현 Sonnet**. 카카오/구글 개발자 콘솔 OAuth 앱 등록은 담당자 수동 작업.

### Step 2-2B — 크레딧 원장 + Polar 상품 개편

- **(a) DB**: 신규 `credit_transactions`(원장), 신규 `webhook_events`(event_id UNIQUE — 멱등성), 잔액 조회 뷰 또는 함수, 원자적 차감 RPC `consume_credit_and_create_report`. `profiles`에 Free 지급 로직 연결.
- **(b) API**: `/api/checkout` 개편(상품 2종 선택 → Polar 세션), `/api/webhooks/polar` 개편(order.paid → 크레딧 지급, 토큰 발급 제거), 잔액 조회 API. Polar 대시보드에 Basic/Pro 상품 생성.
- **(c) 모델 태깅**: **설계 Opus 1회** (원장 스키마·멱등성·RPC 트랜잭션 경계 — 돈이 걸린 로직이라 설계 검증 가치 큼) → **구현은 Fable** (checkout+webhook+RPC+마이그레이션 멀티파일, explore-modify-verify 루프).
- 월간 구독(월 1회 무료)은 이 스텝에서 **제외** — 후순위 Step 2-2G.

### Step 2-2C — 에어비앤비 매물 핀 데이터 적재

- **(a) DB**: 신규 `airbnb_pins`(익명 listing key, lat, lng, dong, bedrooms 등 최소 필드). 노출 필드 화이트리스트를 스키마 주석으로 명문화 — 숙소명·사진 URL·개별 performance 값은 **컬럼을 만들지 않는 것**으로 원천 차단.
- **(b) API**: 적재 스크립트 `npm run fetch:airbnb-pins`(마포구, 사전 1회 적재 + 수동 갱신 — minbak_listings와 동일 패턴), 조회 API `/api/map/airbnb-pins`(로그인 + 크레딧 이력 검증).
- **(c) 모델 태깅**: **설계 Opus 1회** (어느 AirROI 응답에서 좌표를 추출·적재할지 파이프라인 확정 + 갱신 주기 정의) → **구현 Sonnet** (스크립트+API 각 1파일 수준).

### Step 2-2D — /explore 인라인 리포트 (핀 클릭 + 반경 + 패널)

- **(a) DB**: 신규 `analysis_reports`(user_id, 좌표, radius_m 프리셋, bedrooms/baths/guests, report_token(재열람 키), created_at). `report_purchases`는 결제 이력 전용으로 역할 축소(스키마 변경 없음).
- **(b) API**: `POST /api/analysis`(크레딧 차감 RPC 호출 → 리포트 생성 → 데이터 반환), `GET /api/analysis/[id]`(재열람, 차감 없음, 소유 검증). 기존 `/report/[token]` 섹션 컴포넌트 추출 → 인라인 패널 공유. 핀 클릭 → 반경 프리셋(100/250/500/1,000/2,000m) 선택 UI + 원형 오버레이.
- **(c) 모델 태깅**: **Fable** — 컴포넌트 추출 리팩터 + 신규 패널 + API 연동의 멀티파일 자율 작업. 리팩터 범위가 커서 explore-modify-verify 루프가 적합. (착수 전 추출 대상 컴포넌트 목록만 Opus 없이 Claude.ai에서 합의)

### Step 2-2E — 웹 구조 개편 (랜딩 TOBE 전환)

- **(a) DB**: 없음.
- **(b) API**: 없음. 상단 메뉴(홈/분석하기/가격), 로그인·회원가입 버튼, 요금제 소개 페이지(`/pricing`), 랜딩 asis→tobe 비교 섹션. 후기 6개·행사소식은 제외(§4).
- **(c) 모델 태깅**: **Sonnet** — 명확히 범위가 정해진 UI 작업. 디자인은 DESIGN.md 준수.

### Step 2-2F — 전환 정리 + 실오픈 준비

- **(a) DB**: 없음 (검증만).
- **(b) API**: 기존 `/checkout?dong=` 깔때기의 신플로우 연결 확인, 기존 report_token URL 호환 회귀 테스트, Polar 구상품(₩800 테스트) 비활성화, **Polar Payouts 설정(신분인증+정산계좌 — 기존 '남은 작업' 항목 여기서 소화)**.
- **(c) 모델 태깅**: **Sonnet**. Payouts는 담당자 수동 작업.

### Step 2-2G — (후순위) 월간 구독

- **(a) DB**: `credit_transactions`에 reason=subscription_monthly 활용(스키마 변경 없음), 구독 상태 추적 컬럼 or 테이블 소폭 추가.
- **(b) API**: Polar 구독 상품 생성, 웹훅에 구독 주기 이벤트(갱신 시 +1 크레딧) 핸들링 추가.
- **(c) 모델 태깅**: **설계 Opus 짧게 1회** (Polar 구독 웹훅 이벤트 체계 확인 — 문서 실증 필수, 가정 금지) → **구현 Sonnet**.
